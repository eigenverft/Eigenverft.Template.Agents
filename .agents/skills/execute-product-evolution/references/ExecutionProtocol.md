# Execution Protocol — Phases 4–7

All runs follow these gates after a single candidate has been selected and bounded. The agent works autonomously **within the selected increment**, subject to actual tool authority and repository instructions.

**Mandatory workspace rules:** Read and follow [WorkspaceLifecycle.md](WorkspaceLifecycle.md) before creating a branch/worktree or making product changes. The caller's arbitrary current checkout is read-only context; the implementation is isolated in a dedicated feature branch and temporary linked worktree inside the mounted project workspace: prefer ignored repo-local `.worktrees/` where compatible; otherwise choose a safe workspace-local sibling. Clean up only after committing and checking tracked, untracked, and ignored content, preserving the branch.

## Phase 4 — Record: Issue Before Product Changes

1. Inspect the repository's actual issue-tracking convention. Prefer an existing, accessible, suitable tracker or repository-managed issue format. **If neither can be used (for example when an existing tracker is inaccessible or the repository has only general issue summaries rather than a usable per-issue lifecycle), create the minimal repository-versioned fallback** in the isolated feature worktree: `issues/open/<short-topic>-<YYMMDD>[-N].md`. Honor any compatible existing issue directory/layout instead of duplicating it; leave unrelated existing documentation and summaries unchanged. Use the same short dated topic slug as the branch (e.g., `login-errors-261015`; add `-2`, `-3` only for a name collision), checking accessible issues and local/remote branch names; the file path is the issue's stable identifier without a separate generated hash. The initial file must satisfy [IssueRecord.md](IssueRecord.md); create no global issue index or extra administrative files. `issues/done/` is created when the completed issue is moved there in the final closure commit. Do not invent an external issue ID or claim an inaccessible tracker was updated. Respect explicit repository prohibitions on new issue files.
2. Before changing product files, create **one primary durable issue** following [IssueRecord.md](IssueRecord.md) with the original user assignment, selected change and why, baseline, effective phase policies and their provenance, contracts, boundaries, acceptance criteria and risk.
3. Record a real identifier or path and verify it exists durably. **For repository-versioned issues**, create the isolated feature worktree if required, write the initial issue containing the understood request, effective phase policies, selected scope and acceptance criteria, and make a **separate issue-only baseline commit before modifying any product files**. Verify that this commit actually exists and contains **no product changes**. It is a mandatory provenance checkpoint and remains part of the one cohesive review unit. **For external issues**, verify the tracker record before product modification; do not create an artificial duplicate file solely to produce a Git checkpoint.
4. Do **not** stop merely because an external issue tracker is inaccessible or no issue-file convention exists: the repository-file fallback above is authorized for this skill. Stop **Blocked** before product implementation only if even that fallback cannot be safely created, committed and published (for example repository policy forbids it or required Git/write/push access is unavailable). Do not claim a chat note or untracked scratch file is a durable issue.
5. **Make the selected work visible before implementation:** after issue creation and local feature-branch/worktree setup, push that branch to the existing authorized remote and confirm its remote ref exists. Versioned issues publish their issue-only baseline commit; external-tracker issues may publish a new branch pointing at the confirmed integration-base commit, with the external issue containing its details. Link the branch from the external issue when supported. Do not create an artificial empty commit solely to publish a branch, push other branches, or merge. If early publication is forbidden or fails, report **Blocked before product edits** and preserve the issue, local branch and worktree for safe recovery.

## Phase 5 — Implement: Scoped, Tracked Work

1. Follow [WorkspaceLifecycle.md](WorkspaceLifecycle.md): inspect Git state and correct integration baseline, create a task-specific feature branch and a workspace-local linked worktree (prefer an ignored repository-local path; fall back to an accessible sibling where needed), verify its initial state, and **implement only there**. Preserve the user's original worktree, branch and uncommitted work. If issues are repo files, creating the isolation environment may precede persisting the issue, but not product implementation.
2. Before the first product edit, verify that **the primary issue exists and the early remote feature-branch ref is visible**. For versioned issues, also confirm the issue-only baseline commit precedes the first product edit. For external issues, confirm that the tracker issue is recorded and reachable. Break the increment into tasks only when helpful; do not turn each step into a new product objective.
3. **Checkpoint consequential decisions before implementing them:** when new evidence changes the agreed outcome, acceptance criteria, policy, or outer change boundary, stop the affected implementation, append the original-vs-revised decision and reason to the issue, then **stage only the issue file(s), verify the staged diff contains no product changes, and commit that decision separately before coding to the new decision** if the issue is versioned. For an external tracker, persist the change there before continuing and reference the issue in subsequent commits. Do not silently rewrite the initial decision.
4. Implement the **smallest complete** increment, including verified necessary indirect effects. Make **cohesive, meaningful implementation commits** when a verifiable piece is finished or an important recovery checkpoint is needed; explain what each commit implements and reference the issue. Do not require a commit for every edit, and do not mix unrelated scope into decision or implementation checkpoints. Track actual changes, deviations and relevant test evidence in the issue.
5. Additional attractive improvements are **future opportunities**, not automatic work inside this increment.
6. If a gate fails or essential new work would exceed the boundary, stop and return to Assess/Select, transparently amend the existing issue for genuinely same-outcome rescoping, or abandon the pick. Never hide the original scope.

## Phase 6 — Verify: Correctness, Compatibility, Outcome Evidence

1. Run relevant available tests and quality checks; assess consumer contract and behavioral invariants plus UX implications. Examine the actual change set for unintended consequences and unrelated modifications.
2. Compare results with the issue's acceptance criteria, including reviewability and change-budget claims.
3. Distinguish **verification** (code, tests, contracts) from **validation** (observed real consumer value). If consumer value remains unmeasured, say so and avoid asserting proven improvement.
4. Record the tests and their outcomes, regression evidence, any untested areas, residual risks, and explicit reasons if validation is limited.
5. If required checks fail, repair within scope and repeat verification. Otherwise report Blocked/Abandoned with evidence, not Done.

## Phase 7 — Package & Close: End-to-End Reviewability

1. **Verify the implementation before closure.** Confirm acceptance criteria, required tests and protected contracts actually pass. Commit every intended product change and meaningful verification evidence on the **local feature branch** before the closure commit. Review the full issue plus diff for why, what, consumer impact, evidence and remaining uncertainty. An unmet criterion or incomplete code means Blocked/Abandoned, **not** a Done issue or a move into `done/`.
2. **Final dedicated commit for repository-versioned issues:** follow the repository's existing issue storage conventions. In the same issue file created at baseline, document delivered outcome, tests, accepted deviations, remaining risks, and status `Done` meaning **implementation verified / ready to hand off, not merged**. Preserve the original decision history. Record publication of the **final closure commit**, PR/merge and worktree cleanup as **pending/not yet verified**: the early remote branch may exist, but its final HEAD has not been published yet. Move **that same issue** to the established `done/` location, or, for a repository-file tracker without an existing done location, create a `done/` subdirectory of its existing issue root (for example `issues/open/184-topic.md` → `issues/done/184-topic.md`, or `issues/184-topic.md` → `issues/done/184-topic.md`). Prefer `git mv`; do not create a duplicate issue or unrelated tracking system. Stage **only** closure metadata and the issue move, review the staged diff, and make this the **last commit** on the feature branch. No product edits or subsequent issue-file commits after this closure checkpoint.
3. **External issue trackers:** do not invent a repository-file issue or use `git mv`. Preserve the real issue ID and commit references; leave the tracker issue open until after successful remote publication and worktree cleanup, then update/close it according to repository conventions. A PR is optional and must not be assumed to exist.
4. **Publish the finished branch again.** Push the **complete feature branch** to the remote established by the early issue checkpoint (normally `origin`). Verify that the remote ref now points to the final closure commit, not merely the earlier issue-baseline commit. This final push is the success gate for the autonomous cycle, not an optional PR creation or merge. If the push fails or lacks authorization, preserve the local branch/worktree, report publication Blocked, and do **not** claim a successful remote handoff.
5. **Clean up only after confirmed publication.** Verify tracked, untracked and ignored files contain no valuable unsaved work; remove only the temporary linked worktree, without force, and confirm its absence. Retain the feature branch locally and remotely; do not switch/reset the user's checkout. If cleanup is unsafe or fails, preserve the worktree and report its actual path and incomplete state.
6. **Finish the handoff.** For an external tracker, update its verified cleanup/publication outcome and close only when its closure criteria are satisfied. For a versioned issue, the final committed file already resides in `done/` with honestly pending operational fields; report actual remote ref, final commit SHA and cleanup outcome in the final handoff rather than inventing a post-cleanup commit. Say **Done / Ready for Review**, never Integrated unless a separately authorized merge actually occurred. Do not automatically create a PR, merge or delete the feature branch.

## Controlled Returns and Stops

- Revisit Discover/Assess/Select when evidence undermines the selected assumptions; after issue creation, preserve original issue intent and append a transparent decision trail.
- **A duplicate is a rejected candidate, not a reason to create or close an issue.** Check as early as a concrete candidate appears and recheck before allocating any issue/branch/worktree. If no eligible candidate remains, return **No change**. If an unused, unpublished local branch/worktree was nevertheless created, clean up only that disposable setup as described in [WorkspaceLifecycle.md](WorkspaceLifecycle.md). Leave the existing issue and branch that already cover the improvement untouched.
- No-change before selecting a viable increment is a legitimate terminal result. If an issue or remote branch already exists for this invocation, preserve and report it rather than treating the duplicate as an automatic closure task. Other genuine incomplete/blocked work follows the normal Blocked/Abandoned rules.
- Stop after this single increment. The next autonomous evolution cycle requires a new invocation.
