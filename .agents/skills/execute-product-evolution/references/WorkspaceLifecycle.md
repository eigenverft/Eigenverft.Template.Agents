# Workspace Lifecycle — Isolated Evolution Branch and Temporary Worktree

This is a mandatory part of the shared Execution Protocol for autonomous product changes. It is **not** an optional evolution policy and does not alter the separately selected Discover, Assess, or Select & Bound strategy.

## Purpose and Ground Rules

The caller may be in any Git repository directory, on any checked-out branch, with modified files or another agent's work in progress. Treat that checkout as a source of read-only product context, **not** as the location to implement the selected increment.

- Never switch, reset, clean, or commit in the caller's existing worktree merely to prepare this cycle.
- Discovery and assessment remain read-only. Do not create speculative branches or worktrees before a viable increment exists.
- For implementation, use **one dedicated feature branch in one isolated temporary Git linked worktree**. If the repository cannot support a safe isolated worktree, stop Blocked rather than edit the caller's checkout.
- **Keep the temporary checkout within the accessible, mounted project workspace.** Never assume a global home directory, machine-specific parent path, or a host-only path is accessible to an isolated agent runner. Do not use environment-specific external directories such as `_tempWorkTrees/` as the universal default.
- Git permits linked worktrees in either a sibling directory or an ignored nested directory. Choose by actual mount/tool permissions and repository conventions; no path shape is intrinsically required by Git.

## Choose Base and Directory

1. Inspect `git status`, current branch, upstream, `git worktree list --porcelain`, available remote refs and repository instructions. Discover which integration target this repository really uses (for example `develop` or `main`); **the caller's checked-out branch is never the implicit target**.
2. **Before creating the feature branch**, where network access and permissions allow it, run a remote refresh such as `git fetch --prune origin` and confirm the current integration baseline (prefer the confirmed `origin/<target>` tracking ref, recording its SHA). Fetch updates remote-tracking refs; it **does not** mean checking out, resetting or fast-forwarding the caller's branch. Respect existing worktrees and any divergent local integration branches. If fetch fails or is unavailable, do not silently assume the remote state is current: use a known local baseline only when repository/user policy explicitly allows that offline mode, otherwise stop Blocked with the limitation. Never integrate unrelated uncommitted changes into the selected baseline.
3. First honor any safe established workspace/repository convention. Otherwise **prefer an ignored repository-local directory `.worktrees/<topic>/`**, under an accessible checkout inside the mounted project workspace. This keeps the checkout visible and usable in sandboxes mounting only the repository folder. Identify the actual checkout root with Git; do not assume the invoking working directory is the root. If the caller is in a linked worktree, inspect all registered paths rather than blindly choosing a main worktree outside the accessible mount.
4. **Fallback:** If nested worktrees are incompatible with scanners/build tooling or repository layout, use a **sibling directory within the same accessible project workspace** when permissions and mount scope allow it. This is often the cleaner Git layout and needs no nested-directory ignore. Never escape the available workspace just to follow a home-directory convention. If neither a safe nested path nor an allowed workspace-local sibling exists, stop Blocked rather than violating the sandbox or user's workspace.
5. For a nested checkout, **verify that the entire generated directory is ignored by the enclosing checkout before creating it** (for example through `git check-ignore -v`). Respect existing ignore rules; when needed, add a local `.git/info/exclude` rule through the shared Git directory without replacing existing entries. Avoid automatically editing tracked `.gitignore` purely for this agent. Check for tracked path collisions, already registered worktrees, recursive file discovery/build tooling that ignores neither Git excludes nor skip directories, symlinks, and concurrent agents. Exclude nested worktrees explicitly from scanning, packaging, linting and deployment when those tools don't honor ignores. Never stage their contents with the product change.

Preferred layout where nesting is safe:

```text
mounted-project-workspace/
  MyProduct/
    .git/
    .worktrees/                     # locally ignored linked worktrees
      login-errors/                 # local worktree path chosen for this run
```

Safe fallback if the mounted workspace also permits siblings:

```text
mounted-project-workspace/
  MyProduct/
  MyProduct-login-errors/         # linked worktree beside the checkout
```

Both layouts are valid linked Git worktrees, but only choose paths actually accessible and safely managed by the current agent environment.

**User-defined default branch name:** `feature/pevo/<short-topic>-<YYMMDD>[-N]` (for example `feature/pevo/login-errors-261015`). `feature/` retains the usual feature-branch family; `pevo/` already identifies product evolution, so do not repeat an agent prefix in the slug. Use a compact, meaningful lowercase hyphenated topic (include the product area if helpful; normally at most about 24 characters) and the creation date in `YYMMDD` format. **Do not append commit hashes, generated hash-like issue tokens, or a second `pe` marker**: the issue/commit details belong in Git and the primary issue, not the branch ref. Only if that full name is already occupied locally or remotely, add the smallest available numeric suffix `-2`, `-3`, etc.; apply that suffix consistently to the fallback repository-file issue identifier when one is needed. Check existing refs and repository issue names before creating either artifact. This is best effort, not a cross-agent lock: if a concurrent push loses a naming race, stop before product edits and preserve the work for recovery; never force-push over another agent's branch. Choose the local worktree directory according to repository/user conventions and available workspace paths, independently of the branch ref; no special short-name rule is required. Verify the path is unused by other worktrees. CI checkout path limits do not impose naming requirements on a separate local worktree. The short ref still aids the lightweight overlap screen but **does not establish ownership, prove duplication, or reserve an entire product area**; check existing human `feature/` branches and issues too. Respect binding repository naming policies, CI filters and protection rules, and do not rename existing branches. An overridable execution-environment default does not supersede this user-defined convention. **Publish the new branch after recording its issue, before product edits, and again after its Done closure or Blocked handoff commit.**

## Create Only for a Selected, Recorded Increment

1. Complete Discover, Assess and Select & Bound first. **Record one real issue and its intended change before making product modifications.**
2. **Honor the Select & Bound duplicate recheck before creating any issue, worktree or branch.** If the same outcome is already covered, choose another candidate or return No change without creating artifacts; do not repeat the same check unless new information arrived. Otherwise create the isolation environment before any repository-file issue commit or product edit. Then create a **new local** feature branch from the confirmed, refreshed integration baseline and check it out **only** in the new linked worktree (for example `git worktree add -b feature/pevo/login-errors-261015 <workspace-local-path> origin/develop` when that is the verified target). Confirm branch, base SHA, path and initial clean state; do not create the remote branch **before the issue is recorded**, rebase the caller's branch or reuse an arbitrary agent-host-named branch.
3. **Write the original issue inside the new worktree**, using the established compatible file-based issue layout or `issues/open/<short-topic>-<YYMMDD>[-N].md` and **commit that issue alone on its local feature branch**. Do not create it in the caller's original checkout. Verify the issue-only checkpoint before any product modification. Later material decision changes require a distinct issue-only decision commit before implementing the changed decision.
4. **Early remote visibility gate, before product edits:** push only the new dedicated feature branch to the repository's existing authorized remote (normally `origin`; e.g. `git push -u origin <feature-branch>`), then verify the remote ref. The published tip must include the verified issue-only baseline commit. Do not create a filler commit just to force a branch diff. A published branch is a discoverable claim of work, **not** an atomic reservation; competing agents still apply the quick same-area check. On failed/disallowed publication, keep local issue/branch/worktree intact and stop **Blocked** before implementation; never force-push to claim an occupied name.
5. Work, run tests and make **meaningful, scoped implementation commits only in the linked worktree**, distinct from issue-only decision checkpoints. Do not make a commit per trivial edit or let a long autonomous run rely only on an unsaved working tree. Keep the original baseline commit and subsequent decision/implementation history reviewable, without amending them away just to conceal how scope evolved. The caller's branch and files remain untouched. Record actual checkpoint commit and branch/worktree references for traceability.

## Recover from Premature Unused Local Setup

Normally duplicate checks run **before** creating a worktree or branch. If a duplicate is discovered later and this invocation has only created an **unused local** worktree and branch, with no primary issue, product edits, own commits or remote publication:

1. Confirm both were created by this invocation, the branch still points at its recorded starting base, no other worktree uses it, and there are no valuable tracked, untracked or ignored changes. If any condition is uncertain, preserve the artifacts and report why.
2. Remove only that worktree using non-forced `git worktree remove <exact-created-path>`, then delete only its own unpublished, fully merged local branch using `git branch -d <exact-created-branch>`. Remove an ignore entry added solely for this worktree only when it is unambiguously unused; otherwise leave it. Never touch another agent's or a published branch, force-delete, or change the caller's checkout.

Report that the early selection had no eligible increment, along with the actual cleanup; this recovery is not a new No change outcome after implementation. If a primary issue or remote branch already exists, this disposable-setup cleanup does not apply: preserve it and report the situation without automatically creating closure work or deleting published history.

## Done Closure, Blocked Handoff, Remote Publication, and Cleanup

1. **Finish product changes first.** Once verification succeeds, commit all intended product changes and evidence on the local feature branch. Confirm the branch retains the commits and the complete diff is reviewable. Keep the earlier issue-baseline and material-decision checkpoints intact.
2. **Make the issue closure the last local commit.** Record the verified implementation outcome, tests, deviations and status `Done` in the original issue and **move that file to the established `done/` destination in the same dedicated final commit** (using `git mv` where applicable; create `done/` under the existing issue root if no completed-issue directory exists). Preserve its identifier, do not leave a duplicate under `open/`, and stage only that closure/move plus directly related issue metadata—**no product code changes**. Verify the staged diff and actual final commit. Do not mark unsuccessful work Done or move it to `done/`.
3. **Update the already-published feature branch for the successful handoff.** The early issue checkpoint (and any additional coherent implementation checkpoint pushes) makes ongoing work visible but does not finish the cycle. After the final closure commit, push the **complete dedicated feature branch only** to the same remote and verify the remote ref resolves to the exact final local commit. **Do not automatically create a PR, merge into `develop`/`main`, reset the caller's worktree, or delete the remote branch.** If authorization or push fails, preserve the original linked worktree and local branch and report Blocked / Publication pending; the work is not successfully handed off remotely.
4. **Only after confirmed remote publication, remove the temporary linked worktree.** Verify that all important work is committed and remotely retained; examine tracked changes, untracked and **ignored** contents (`.env`, build artifacts, data, symlinks/junctions). Use ordinary non-forced `git worktree remove <exact-created-path>` and verify via `git worktree list` that the linked path is gone. Never use `--force`, delete arbitrary directories, or prune others' worktrees.
5. **Keep the remote feature ref; remove only this run's local feature ref after safe worktree cleanup.** The remote branch is the review/integration handoff; a local branch on the execution machine is unnecessary afterward. First confirm the worktree was removed, no other registered worktree checks out the branch, and the exact branch was created by this invocation (never delete the caller's, another agent's, or a pre-existing branch). Recheck that the local branch tip still equals the published final commit and the remote feature ref still exists at that exact SHA. Then delete only this local branch (prefer `git branch -d -- <exact-branch>`; if Git's merge check alone rejects it, `git branch -D -- <exact-branch>` is permitted **only** after all those identity, SHA, remote-publication and worktree checks succeed). Never force-remove worktrees, force-push, or delete the remote branch. If any check fails or removal is unsafe, leave the local branch intact and report the reason; do not risk losing unpublished work.
6. **Report actual state.** The final Done closure commit follows verified initial branch publication but precedes publication of its **final HEAD** and cleanup, so it can truthfully say implementation Done while final-head publication, integration and cleanup remain pending; report verified remote branch, closure commit SHA, worktree removal and local branch deletion outcomes afterward in the final handoff. Distinguish **implemented**, **committed**, **published/Ready for Review**, and **integrated**; only the last requires a separately authorized merge.

**Blocked handoff after an issue exists:** If safe completion or required verification is prevented, do not mark Done or move the issue to `done/`. Commit useful, reviewable work on the existing feature branch when safe, clearly identifying unverified implementation; preserve anything that cannot be safely committed. In the **same issue file**, record the concrete obstacle, actual progress, missing verification and resumption condition; move `issues/open/<same-filename>` to `issues/blocked/<same-filename>` (or the equivalent existing issue root) in a dedicated issue-only status commit, keeping the identifier unchanged. Push the same branch and **verify that the remote ref contains both saved work and the Blocked issue**. If push is impossible, keep local branch/worktree and report the remote as stale; never force-push or invent a remote status. After successful publication, remove the temporary worktree only when the usual non-forced safety checks confirm no valuable local work would be lost; then apply the same verified, narrowly scoped local-branch deletion rule as for Done. Retain the **remote** feature branch for future verification or authorized integration. If either local cleanup action fails, preserve what remains and report its actual state.
