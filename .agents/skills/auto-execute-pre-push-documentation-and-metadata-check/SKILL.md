# Auto Execute Pre-Push Documentation and Metadata Check

Before publishing requested changes, check whether their relevant existing documentation and descriptive publication metadata remain accurate and complete.

The push request is the trigger and includes necessary documentation and descriptive metadata corrections in a separate commit when needed; a separate commit request is not required. It does not authorize unrelated changes or a release.

- Use the intended branches and destinations established by the publication workflow. Inspect the outgoing changes, including pending work covered by a commit-and-push request, rather than relying only on commit messages. Use targets belonging to the branch being published; do not switch checkouts or absorb unrelated work.
- Before detailed review or editing, independently discover and lock the initial set of relevant existing repository-owned targets using outgoing changes, repository conventions, and package or release configuration. Follow authoritative sources, not every apparent copy. Expand this set only when a newly verified consequence requires another target.
- Illustrative hints only: repository or package READMEs, release notes or changelogs, documentation folders, and descriptive fields in manifests, project files, packaging configuration, or source. Such fields might contain descriptions, keywords, or project and documentation links. These are not required files, fixed paths, or an exhaustive checklist. Discover other relevant targets independently; checking these examples alone does not establish coverage.
- Source-file edits are limited to explicit descriptive publication metadata. Do not modify implementation code, source comments, or inline code documentation, including comments used to generate documentation; do not bypass this boundary by editing generated substitutes. Such gaps belong to a separate coding task.
- Check for concrete documentation or descriptive metadata consequences of changed behavior, interfaces, configuration, requirements, compatibility, setup, or usage. Internal-only changes do not automatically require user-facing notes. Describe only verified changes within the publication scope, not unrelated working changes or speculative plans.
- Consider the intended audience and purpose of each target, using established conventions and reliably known repository visibility as context. Visibility alone does not determine the audience. Preserve the established style, but do not treat existing content as exhaustive coverage: add necessary information to an appropriate existing target when the outgoing changes require it.
- Leave wording unchanged when it remains accurate and adequate. Make small wording corrections only when they resolve a concrete misunderstanding or inaccuracy caused by the outgoing changes, not merely because another phrasing seems preferable.
- Check version references in relevant documentation and descriptive publication metadata against their authoritative sources and intended meaning. Consider repository-specific formats and manually assigned or computed versions. Update references only when a mismatch and the appropriate replacement are reliably established for the outgoing state. Preserve historical entries, compatibility ranges, and illustrative examples; do not invent future versions or alter versioning inputs.
- Maintain existing targets only, adding or correcting content within them only where the outgoing changes make it verifiably necessary. Preserve established structure and distinguish unreleased changes from released behavior. Do not create new documentation files or metadata structures, invent release facts, or change release identity, authoritative version inputs, Git tags, dependency requirements, executable behavior, or remote release state under this check.
- Commit this check's corrections in a separate documentation-and-metadata-only follow-up commit before the push, even when implementation commits are still pending. Follow existing commit rules and keep the correction independently revertible; never fold it into an implementation commit, amend, or rewrite history. Preserve unrelated working changes and staged selections. Ask only when required content cannot be established or resolving the gap would exceed this maintenance scope. Do not block publication for optional documentation or metadata preferences.
- Recheck the affected targets against the final changes being published. When no necessary gap exists, continue silently rather than producing a compliance report. Otherwise mention only the corrections made or the concrete unresolved blocker.
